# Authentication and account administration

The admin listener serves login, required password change, settings, API-key rotation, user management and explicit administrator impersonation. The Leptos UI uses cookies and the preserved HTTP API. Resource management is documented in [resources.md](resources.md).

## Passwords and migration

Existing Go bcrypt hashes remain byte-for-byte unchanged during migration and login. The Rust bcrypt verifier preserves Go's historical 72-byte truncation semantics, including longer supplied passwords. Creating an account or changing a password stores a salted Argon2id hash and verifies the entire UTF-8 input. Ordinary login does not silently rewrite a legacy hash. Two accounts can therefore use different hash formats in the same database without a global conversion or password reset.

New passwords require at least eight UTF-8 bytes, matching the existing policy, and accept at most 1024 bytes. Confirmation must match, and the password-change workflow rejects reuse. Argon2id uses the library defaults of 19 MiB memory, two iterations and one lane. Four admitted hashing/verification operations run on blocking workers per server; saturation returns a retryable failure. Stored hash parameters are untrusted: bcrypt costs above 16 and Argon2 parameters above 64 MiB, ten iterations or four lanes are rejected before expensive work. A manually customized legacy hash above those limits needs an operator-assisted password reset; the database is not rewritten to hide that incompatibility.

Startup adds separately versioned Ruphish authentication tables after validating the legacy schema. It creates a verified pre-upgrade SQLite snapshot even when all Go migrations were already applied. IDs, ownership, API keys, established hashes and history are preserved. Unknown/future/partial authentication schemas fail closed. Password changes and account generation changes commit atomically; failed writes preserve the prior credentials and authorization state.

The old Go executable cannot verify Argon2id. To roll back, stop all processes and restore the preserved pre-upgrade snapshot to a separate configured database path. Later Rust writes are outside that recovery point. Do not run Go and Rust against the same database during cutover.

## Browser and API behavior

Changing your own password requires the dedicated password workflow: POST `/settings` verifies `current_password` with `new_password` and `confirm_new_password`; required initial setup uses `/reset_password`. A nonempty password in a generic PUT `/api/users/{id}` targeting your own account is rejected for both browser sessions and API keys. Authorized administrators can still reset other accounts through that API. Omitting the password retains it.

Browser sessions use tower-sessions 0.15 with signed HttpOnly, SameSite=Strict cookies and SQLite storage. TLS adds Secure and the __Host- prefix. The signing key persists in the database; ordinary restarts retain established sessions. Login expires after twelve hours without sliding renewal. Login and identity changes rotate session IDs. Logout deletes the stored session; delayed ordinary saves update only an existing unexpired record and cannot recreate it. Account generations revoke sessions after password/account changes, while current roles and permissions are loaded on each request. A request already authorized before revocation can finish; logout is not a transaction cancelling every in-flight operation.

Go browser cookies do not transfer to Rust. The sidebar username button opens an anchored account popup with My account and Sign out. It stays within the visible viewport and supports Escape, outside dismissal and keyboard focus. Sign out posts directly, asking to discard only when a draft is unsaved; a failed request leaves the session and draft intact. GET /logout still displays confirmation for direct legacy navigation; POST /logout performs logout. The additive /auth/session endpoint supplies browser identity and a CSRF token, never an API key. axum_csrf protects browser mutations, including login, and the server checks supplied Origin/Referer and Fetch Metadata. csrf_key changes invalidate prior CSRF tokens. Legacy trusted_origins entries use host[:port] with the listener's scheme; explicit http(s) origins are also accepted. Same-origin validation uses HTTP/2 URI authority or the HTTP/1.1 Host header and rejects conflicting authority values. Forwarded headers are not trusted for peer identity or scheme. Reverse-proxy trust configuration is not implemented.

Automation retains query/form API keys and Authorization Bearer credentials. An explicitly supplied invalid key cannot fall back to an authenticated browser cookie. Locked accounts and accounts requiring a password change cannot use API keys. Key rotation creates 32 OS-random bytes encoded as 64 hex characters and immediately invalidates the old key. Keys remain retrievable through the authorized legacy account API, so database and backup confidentiality remain essential. CORS permits explicit-key clients and Authorization preflight; it does not allow credentialed cross-origin browser access.

Authorization checks permissions, ownership, lock state and password-reset restrictions. Deleting your own account is forbidden (403), even when another administrator exists; another authorized administrator must perform the deletion. User deletion removes owned records transactionally while preserving other owners and shared targets. Deleting, locking or demoting the last unlocked administrator is rejected inside the write transaction. Impersonation records both actor and effective user, requires a current administrator, shows a banner with exit, and prohibits account/credential management while active.

The browser rechecks the current identity when a tab regains focus or becomes visible. An unchanged session preserves open forms; lost authentication redirects to sign-in, while changed identity or permissions reloads the current page. A protected API response of 401 immediately blocks the stale view. The UI sends x-ruphish-client: browser to request a clear session-ended error; this marker only changes error presentation and grants no authority. Ordinary API clients retain legacy missing/invalid-key responses. Logout ends that login only; another independently authenticated browser stays signed in.

Successful account deletions record actor_id and user_id so later investigation can distinguish the caller from the deleted account.

Login admission allows a burst of five attempts and refills five per minute per connection IP. Forwarded IP headers cannot bypass it. This limiter is process-local, so multiple server processes do not share one global quota. Authentication request bodies have a 16 KiB limit and ten-second deadline. Ordinary logs omit passwords, keys, cookie values and query strings.

## Account screens

My account at `/settings` shows username, role and API access. The API base URL can be copied; the API key is fetched only after Reveal key and can then be copied or hidden. Replacing the key requires confirmation. Clipboard failures offer manual copying. Change password opens `/settings/password`; its form continues to submit to legacy POST `/settings`. Successful changes return to My account with confirmation and revoke other sessions. Required initial setup stays at `/reset_password`. Impersonation continues to block account and credential management.

User management at `/users` is a full-width list. Create user opens `/users/new`; each Edit action opens `/users/<id>/edit`. Successful saves return to the refreshed list with confirmation. Cancel returns without saving; links, Back/Forward and sign-out warn about unsaved form changes. Fields are disabled while loading or saving; failed loads cannot become new accounts. Failed saves retain non-secret values and clear the entered password. Existing user APIs, default password setup, custom roles, self-deletion protection and impersonation restrictions remain unchanged. Both direct browser routes require administrator permissions. Users and resources share management page, header, table, field, form, Save, Cancel footer, empty-state and deletion-dialog presentation. User-specific role, password, impersonation and API logic remains separate. Save is at the top right and Cancel changes at the bottom left. The Users list supports username search; deletion opens a native modal with Cancel initially focused, request errors inside the dialog, and controls disabled while deleting.

## Manual checks

Use an isolated database and the startup instructions in [startup.md](startup.md). Build current assets before running the executable. All example passwords below are synthetic test inputs, never production credentials.

1. Open the admin address, sign in with the printed temporary password, and confirm navigation requires a password change. Try `short`, mismatching confirmations, and reusing the temporary password; each must fail. Set `Manual-admin-passphrase-42!` in both fields and confirm the authenticated workspace opens.
2. Log out and confirm Back/reload cannot recover an authenticated page. Try a wrong password, then the correct one. Restart the server after establishing the password; confirm it does not print another initial password and an existing session remains usable.
3. Open the username button at the bottom of the sidebar, choose My account, then Change password. Try an incorrect current password, then change to `Français-é-😀-manual-passphrase-43!`. Confirm a second signed-in browser loses its authenticated session and the old password no longer logs in. Check both Unicode entry and confirmation visually.
4. Reveal the API key, cancel rotation once, then confirm rotation. Check the old key receives 401 and the new key can access the authorized API. Reload and confirm the key is not unnecessarily displayed.
5. Create a normal user, sign in using a separate browser profile, and confirm it cannot open user administration or retrieve another account. Change its own password and confirm success. An administrator should be able to edit, lock, unlock and delete the test account; a locked account must lose both browser and API access.
6. Create another administrator. Your own Delete button must be disabled, and a direct self-delete request must return 403 without changing the account. Delete a different disposable account and confirm it disappears. Demoting or locking the last unlocked administrator must fail without partially changing it.
7. Use View as on a normal account. Confirm the banner identifies impersonation, administrator controls are unavailable, and account/credential changes are blocked. Exit and confirm the original administrator identity returns. Reload during impersonation and check the banner remains accurate.
8. For migration testing, stop the server and point a disposable configuration at a copy of the synthetic Go fixture. Login as admin with `FixtureOnlyPassword42!`. Confirm migration produced a snapshot, login preserved the bcrypt hash, and changing the password stores Argon2id. Never overwrite your real installation for this check.

9. Keep Users open in two tabs sharing one browser login. Sign out in one, then return to the other; it must redirect to login with a session-ended message. Repeat with a password change from another independent browser. A protected request made before the focus check completes must also redirect on 401. A separate browser's independent login should survive an ordinary logout.
10. Type an unsaved form change, switch tabs and return without changing authentication; the draft must remain. Scroll a long Users/editor page: on desktop the sidebar should remain bounded to the viewport with its own overflow, and narrow layouts should still scroll normally.

11. Open the sidebar account button with Enter/Space. Confirm focus moves to My account; Escape restores focus to the button. Tab out or click elsewhere to dismiss. At a narrow width and 200% zoom the popup must stay reachable without covering controls off-screen. On desktop, scroll the navigation and confirm the account button stays at the bottom.
12. My account must show no password form. Copy the hidden API key and paste it into a local scratch buffer: it must contain the real key while the field stays masked. Toggle the eye button repeatedly: its accessible pressed state and icon change, while the key field width stays fixed. Copy the revealed key as well, hide it, and reload to confirm it starts hidden. If clipboard permission is denied, show a useful error without displaying the hidden key; reveal/select/manual copy remains available. Recheck at a narrow window width and 200% zoom. Open Change password, enter values, then cancel a navigation-discard prompt and confirm the form remains. Successful change returns to My account with a confirmation. Reload `/settings/password` directly and recheck first-login and impersonation restrictions.
13. With a resource draft open, choose Sign out and cancel the discard prompt; confirm the draft and session remain. Accept and confirm sign-out reaches login. To test connection failure, stop the local test server before signing out: the menu must report failure and retain the draft. Restart and retry.

14. Compare Users with Groups: headings, table rows, search controls, form spacing and action placement must match. Search for an existing username and for a nonexistent one; distinguish no matches from a failed load. Open Delete for a disposable user, press Escape or Cancel, then repeat and confirm deletion. Tab must stay in the dialog; failure must remain visible inside it. On Users, confirm the list occupies the available width and no form appears beside it. Create user must open `/users/new`. Enter a disposable username and password, cancel a navigation-discard prompt, then create the account: return to the list with confirmation. Edit must open `/users/<id>/edit`, load the selected account and return after Save changes. Cancel must leave stored data unchanged. Try a duplicate name, a missing/invalid edit ID, direct route refresh, and access from a normal account. Failed saves must retain non-secret input; password fields must clear.

Automated executable tests cover malformed requests, forged/expired/replayed cookies, CSRF/origin failures, live permission changes, concurrent last-administrator operations, two server processes, SQLite failure injection, independent Go response fixtures and mixed password formats. Manual UI acceptance remains separate from those backend guarantees.

## Deferred UI issue

Manual acceptance found that a deleted user could remain visible in the Users table until a full page reload. This remains an open UI refinement. Mutation/list refresh and reactive rendering need investigation; the root cause is not established. Acceptance requires successful deletion to remove the row without reloading, failed deletion to preserve the row, and late responses not to restore deleted users. Existing backend deletion tests do not establish that browser-state behavior.
