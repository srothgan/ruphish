Documentation source lives in `docs/`. The Astro website imports it into Starlight under `/docs/`. Edit the original Markdown or MDX; `website/src/content/docs/` and `website/public/docs-files/` are generated inputs.

## Choose the canonical home

| Reader task | Home |
| --- | --- |
| Install and complete a first local campaign | `getting-started/` |
| Work with resources, campaigns, and results | `user-guide/` |
| Manage a team or host and maintain an installation | `administration/` |
| Integrate through HTTP endpoints | `api/` |
| Move from Gophish | `migration/` |
| Build, change, and test the project | `contributing/` |

The root `CONTRIBUTING.md` owns contribution and review expectations. README introduces the product. Installation upgrades belong in hosting and maintenance; database conversion and API differences from Gophish belong in migration. Give detailed facts one home and link to them from other journeys.

## Write for a concrete task

Begin with what the reader can accomplish and the prerequisites they need. Use numbered steps for ordered actions, code blocks for copyable commands and payloads, and tables for fields or meaningful comparisons. Explain the expected result and relevant recovery steps.

Use direct language, sentence-case headings, and current UI labels. Distinguish application accounts from recipients, SMTP acceptance from inbox delivery, and observed events from inferred behavior. Preserve exact API fields, paths, error codes, and template expressions.

Keep each prose paragraph and each list item on one source line. Do not manually wrap Markdown prose. Use descriptive link text and meaningful alternative text for images.

Verify behavior against the implementation and tests before writing it. Existing docs are leads, not proof. Use synthetic data and explicitly marked example values. Do not publish credentials, recipient data, or local fixture state. A source check, an executed example, and a complete workflow test provide different evidence; report them accurately in the contribution.

## Add or reorganize a page

Use lowercase, hyphenated paths and an `index.md` for a group overview. Supply frontmatter:

```yaml
---
title: A concrete page title
description: What the reader can do or understand after reading this page.
sidebar:
  order: 210
---
```

Starlight supplies the page's H1 from `title`; start body sections at `##`. Use relative source links such as `[Architecture](architecture.md)` and preserve heading fragments. The importer converts documentation links to site routes and links to repository files outside `docs/` to GitHub URLs. Assets under `docs/assets/` are published separately.

Assign explicit order to every page in an ordered chapter. Starlight orders an autogenerated folder using its lowest descendant order, so use non-overlapping ranges for sibling groups. This chapter uses 100-series setup pages, 200-series development guides, 300-series testing pages, and 400-series maintenance pages. Check the rendered sidebar and Previous/Next destinations after moves; numbering alone does not prove the reading order.

Use plain Markdown unless the page needs a supported MDX component. Existing MDX pages demonstrate the installed integration. Consult the installed Starlight version before using component APIs. For an unfinished page, `draft: true` excludes it from production; sidebar hiding alone does not exclude a route or its content from publication. The importer excludes paths beginning with `.` or `_`.

## Preview your changes

Use Node **24.x** for the website. From the repository root:

```sh
cd website
npm ci
npx astro dev --host 127.0.0.1 --port 4321
```

Open **http://127.0.0.1:4321/docs/**. The server watches the original docs and updates the generated content. Stop it with **Ctrl+C**.

For complete search and production rendering, run from `website/`:

```sh
npx astro build
npx astro preview --host 127.0.0.1 --port 4321
```

Pagefind search is generated during the build. Stop the dev server before starting preview on the same port. Every build uses the canonical site URL `https://www.ruphish.com` from `website/astro.config.mjs` for the sitemap and page metadata. A generated sitemap does not establish that documentation links are correct.

## Verify a documentation change

Check relative file targets and heading fragments, JSON/YAML syntax, shell choice, working directory, and the source of every substantive example. Inspect the rendered page for heading hierarchy, readable tables, and code blocks. Follow incoming links and the intended reading sequence after renaming or merging pages.

Run the relevant website checks from `website/`:

```sh
node --test tools/navigation.test.mjs
npx astro check
npx astro build
```

The navigation test covers the website's mobile menu; it does not assert documentation sidebar order or links. A passing build does not guarantee every link target or example is correct. Review the affected rendered links and contributor journey as well. Documentation-only changes do not need a Rust product build.

## Change the website implementation

`website/src/` owns the site UI, `website/tools/docs.mjs` owns documentation import/link conversion, and `website/astro.config.mjs` owns Starlight integration. Product UI changes belong in `crates/ruphish-ui/`, not here. Follow [website development](../../../website/README.md) for the full test set, installer/release-discovery boundaries, and asset workflow. Use [JavaScript validation](../testing/validation-commands.md#javascript) for maintained site scripts.
